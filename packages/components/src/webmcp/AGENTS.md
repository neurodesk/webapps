# Browser agents (WebMCP) contract

- Every app's WebMCP tools come from its `automation.json` (`packages/components/src/webmcp/tools.js`); an app writes no tool code. The shell imports `webmcp/page.js` only when the browser exposes `document.modelContext`, and it reaches the app through the `neurodeskAutomation` global. Keep `automation/` free of imports from `webmcp/`, `ui/` or `elements/`: command lines import the automation barrel, and `test/webmcp-shell.test.mjs` fails otherwise. A module the shell loads goes into `SHELL_COMPONENTS` with everything it imports.
- The agent's questions and file requests are the shared `createAgentPrompts()` dialogs. The shared Privacy statement about agents is `shared.agents` in `registry/app-information.yml`. A dialog that names state (`confirmFetch`, `confirmFiles`, `confirmResume`) takes a function for its request, reads it when it shows and again on Allow, and resolves to the request allowed; the tool applies it only while it is still current. A request that changed is shown again in place, keeping the dialog's buttons and focus; requests compare by what they name (roles, names, sizes, the checksum a file was verified against or the File itself, the run), never by a counter, and on the third change the dialog closes as declined. Every way of closing an agent dialog (Escape, the close control, the backdrop) is Decline; `scripts/test-agent-prompt-browser.mjs` checks each with real keys and presses in Chromium. `packages/components/test/agent-prompt.test.js` enumerates the prompts and fails on an unclassified one.
- The files an agent holds and the runs it started belong to one examination (`webmcp/tool-inputs.js`), and an app writes no code for it. The guarantee rests on one event fact only: whether the person did anything trusted in the page since the agent last had their Allow. `site/theme.js`, the first script of every app page (the composite build places it before every other script, and `test/catalog-sites.test.mjs` fails on a built page where another comes first), hands each press, key, input, change, paste, wheel, drag and drop to the tools from a capture listener on window, before any listener of the page or the shell (the page drop included) can stop it; same-origin frames get the same listeners from the first animation frame after each new document appears, a frame's navigation is itself a touch, and a frame showing another origin's document is followed every animation frame, so a document of the page's origin replacing it is watched from its first frame and the change is a touch. After a touch, the agent gets nothing from the examination without the shared resume dialog: the next run, `runs_get`, `runs_cancel` or `outputs_download` shows it, calls waiting on one touch share it and its one answer, and it names exactly what Allow hands back, the latest run's own inputs (the files of the roles its operation read and the root of each url input) and the files the agent keeps. Allow discloses only that run, from what the tools recorded when it ended: `runs_get` returns the recorded report, and `outputs_download` saves only while the page holds that run with the output checksum the report recorded (else `RUN_STALE`); every app's outputs come from `registerAppAutomation`, which keeps each run's own files, so none needs to refuse. Earlier runs of the examination stay withheld, and Decline ends it. The dialog says the agent gets that run's results even if the page shows others now: a run the person starts in the app does not reach the automation, so the tools cannot tell it from browsing. `interactionEffect` also ends the examination (earlier runs return `RUN_STALE`, nothing to resume) on a pick in any file input, a drop of files, the example selector, a handoff, `automation.reset()`, and on a touched examination a list change reported with `nd-files` or files the page puts on a classified input; this only spares a pointless dialog, and nothing depends on an end being recognised. Not counted: the agent's dialogs, the shared bar and its dialogs, page scrolling, pointer movement, modifier keys and focus.
- Every tool call is bound to the turn it began in, which every counted event replaces: it reaches the page, the prompts and the fetchers only through `examinedCall` in `webmcp/tools.js`, which checks the turn before each request and after each answer, so a call the person interrupts returns `EXAMINATION_CHANGED` and does nothing more, and its queued prompts are dropped unshown. A new tool gets this by taking its I/O from the `call` argument and passing `call.waits` as its prompts' and fetches' signal; the components test that enumerates every tool fails otherwise. `tools.js` lists every error code once. The read-only viewer tools read what the viewer shows whatever the examination's state, since the person sees the same image.
- `pageFiles` lists what the page's classified inputs (light DOM or open shadow roots), drops and handoffs received, not what it shows: an app may refuse a file or load another through its own code. `inputs_use_page_files` always shows the person the files before the agent gets them, and a run or viewer load the tools start clears the record. No consent depends on the record being current: a stale entry only leads to that dialog, and the press on a remove or clear control touches the examination. So the tools change no app's list reporting, which the shell's Undo reads (`nd-files`): keep the page drop, the shared file controllers and the apps' list handlers free of WebMCP changes.
- An example file's `role` serves the page's example selector. When it differs from the contract's input role, map it in the example's `automation` field (`roles`, `files`, a `reason` for files left out) or state `automation.unavailable`. Page parameters that are not contract parameters are translated in `automation.parameters`. Mark a contract parameter `required: true` when the operation cannot run without it; every example must then give it. `node scripts/webmcp-examples.mjs` lists the problems and `test/webmcp-examples.test.mjs` fails on one.
- Every tool checks its input against the schema it publishes (`webmcp/schema.js`), which knows only the keywords the table uses and judges numbers as the page's zod schema does. `viewers_niivue` offers the nv-mcp methods `webmcp/niivue-methods.js` classifies as read, display, fetch or replace, and of each only the parameters `NIIVUE_PARAMETERS` lists; classify a method or parameter nv-mcp adds there, and audit the offered ones again when nv-mcp changes (`NIIVUE_AUDIT`, `NIIVUE_PARAMETER_EFFECTS` and the parameter check against nv-mcp's `CORE_SCHEMAS` in the components tests fail otherwise). A taken parameter only reads, changes the display or names the approved file; one that removes, moves or converts what is loaded is refused (load_mesh's `replace` among them), and `load_volume`'s consent says it replaces the images shown. The tool fetches an address only after the person allows it, refuses a redirect, and gives NiiVue the bytes, never the address; a method whose payload can name further addresses is denied.
- `node test/webmcp.smoke.mjs` (after `pnpm build`) drives every app's tools in Chromium's own WebMCP and fails without it (`WEBMCP_STAND_IN=1` substitutes a stand-in); it checks that each light-DOM file input, folder inputs included, lists the files picked in it (what the tools offer the person to confirm, not what the app accepted), and counts inputs in shadow roots without checking them. With `WEBMCP_RUNS=1` it runs every loadable example through the tools (`WEBMCP_EXAMPLES=first`: one per app); a run that does not complete fails unless `test/webmcp-run-skips.json` names the app with the outcome it expects (`timed out`, `run failed` with an error pattern, `no loadable example`) and why. `node test/webmcp-examination.smoke.mjs` drives the examination, resume, permission and prompt cases a person can cause (`WEBMCP_CHECKS` narrows it by label). `node test/webmcp-interaction.smoke.mjs` lists each app's controls once it is ready (tools registered, example selectors filled, page quiet): every classified file and folder input, every remove or clear button, and every visible select, checkbox, text field and canvas, at most `WEBMCP_INTERACTION_MAX` (40) per app, reporting how many it found. Selects change to another option by keyboard. After each action it waits for the work the action started to finish as the app reports it (example selectors loading, a run's ×), and it answers the agent's file request only in the open dialog. For each, the agent holds a file, the person acts, and with no Allow given the agent must not get the file back: the examination must be ended, or touched with the agent's next run showing the resume dialog naming the held files, which the test declines. The expectation comes from the page, not from `interactionEffect`: every action must end the examination or touch it with that resume dialog, whatever it changes in the page. The status bar's cancel × is not listed as a remove button. An action it could not perform, an app where it performed none, and an app with no file role fail unless `test/webmcp-interaction-skips.json` names them with the reason. The site-catalog job runs all three, the examination smoke over its fixed apps and the other two over `SMOKE_APPS`.
- A url input's consent names the address the app reads under, computed by the app's own function passed as `sourceRoots` to `registerAppAutomation` (ZARRo passes its store normaliser), never a copy of it. The app keeps every read of a load the agent started under that root and follows no redirect, where it fetches (ZARRo: `src/confined_store.js`); loads the person starts are not confined.
