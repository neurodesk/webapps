# Standalone container research

Checked 2026-09-15 UTC, 2026-09-14 in the workspace timezone, against the official Neurodesk container source at [commit f985e28](https://github.com/neurodesk/neurocontainers/tree/f985e28c5a78285bed756c71e9abd83e52588a9f). This note covers container assignment for all 24 catalog apps. The [standalone rollout plan](standalone-rollout-plan.md) covers compiled GitHub release assets.

## Evidence and release rules

The [recipe catalog](https://github.com/neurodesk/neurocontainers/tree/f985e28c5a78285bed756c71e9abd83e52588a9f/recipes) describes builds. The [release records](https://github.com/neurodesk/neurocontainers/tree/f985e28c5a78285bed756c71e9abd83e52588a9f/releases) identify accepted application versions and build dates. Neurodesk generates its deployment inventory from those release records, as defined by [update-apps-json.yml](https://github.com/neurodesk/neurocontainers/blob/f985e28c5a78285bed756c71e9abd83e52588a9f/.github/workflows/update-apps-json.yml). A recipe alone is insufficient evidence that a container is released.

The release IDs below use `name_version_builddate`, which identifies the dated Neurodesk container. They are verified against release records, not live image pulls. Before adding a Docker/Apptainer download command to the UI, resolve its registry manifest and pin its digest. The [publishing workflow](https://github.com/neurodesk/neurocontainers/blob/f985e28c5a78285bed756c71e9abd83e52588a9f/.github/workflows/build-app.yml) supports multiple registries and both legacy and newer tag naming. Do not construct an unverified registry URL from a recipe version.

An upstream container can offer the same scientific method without reproducing this repository's model export, preprocessing, execution engine, defaults, or complete workflow. The Standalone dialog must name that difference. Where no matching container exists, the assignment below is a proposal to publish a new Neurodesk recipe after the compiled app release works.

The clarified airgap requirement also applies to every container: include all required models and runtime assets in the released image. Accepted release records do not establish this property. Verify installation and first execution without network access or prior caches, update any container that fetches weights at startup, and publish prebuilt SIF images for offline transfer. See [the shared desktop and HPC architecture](webapps-desktop-architecture.md).

## QSMbly compatibility

The local [Rust manifest](../../apps/qsmbly/rust-wasm/Cargo.toml) pins `qsm-core` v0.23.0 and `qsmxt-config` v9.11.0. Therefore `qsmxt_9.11.0_20260807` is the first container to validate against generated commands and TOML configuration. This is a compatibility candidate inferred from matching version pins, not a completed parity test.

The catalog also has a newer [QSMxT 9.19.1 release dated 20260914](https://github.com/neurodesk/neurocontainers/blob/f985e28c5a78285bed756c71e9abd83e52588a9f/releases/qsmxt/9.19.1.json). Updating to it requires testing the serialized configuration, defaults and selected reconstruction methods. Do not silently replace the matched version with the newest version.

The [QSMbly container recipe](https://github.com/neurodesk/neurocontainers/blob/f985e28c5a78285bed756c71e9abd83e52588a9f/recipes/qsmbly/build.yaml) is at 0.11.1, exposes `qsmbly start` and describes a local WebAssembly application. Its latest accepted release is 0.11.0. Neither establishes release of the current app's compiled native pipeline.

## Checks before wiring container links

1. Resolve the accepted release's registry manifest and record an immutable digest, supported architecture, and working pull command. Do not infer released ARM support from a recipe's architecture list.
2. Run the documented example against a small appropriate fixture and verify expected outputs. For upstream alternatives, document the model or pipeline differences explicitly.
3. For every new container, consume the same GitHub binary artifact offered in the app's Standalone dialog, then publish the Neurodesk recipe and accepted release record.
4. Keep source model assets in the approved Hugging Face dataset with pinned manifests and checksums, and include their verified copies in each released image. Test with no network and empty caches. Container or model redistribution conditions remain part of the release packaging work.
5. Populate Standalone with verified binary downloads and the assigned container. Pending recipe names belong in this plan, not in user-facing download links.
