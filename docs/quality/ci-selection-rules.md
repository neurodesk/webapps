# CI selection, gates, budgets and site checks

Detailed reference extracted from root [AGENTS.md](../../AGENTS.md) (`## CI scope`). See also [CI development tiers](ci-development-tiers.md).

`scripts/lib/app-plan.mjs` picks the apps a change tests from the workspace graph (`scripts/lib/workspace-graph.mjs`): the packages, `exes/` directories and root files (`scripts/`, `test-utils/`, `registry/`, `test/`) each app reaches through a workspace dependency, a relative path, a repository-root path or an import. A change selects the apps that reach it; `changedPathsFromGit` reads the diff NUL-delimited with both sides of every rename and copy, and a diff it cannot read selects every app, the site build and the easter egg instead of nothing. A path named only in a whole-line `//` comment of a root file (not a `///` directive) is not a reference. A file under `apps/<id>/` also selects every app whose code names it, or a directory holding it, by a relative path (`appReaders`: a kit it stages, a fixture its tests read; globs, interpolated and root-relative paths are not seen). A root file that ci.yml's per-app jobs run (`app-tests`, `browser-e2e`, `browser-e2e-gpu`) selects every app; one only the site jobs run (`composite-site` and the jobs that wait for it) selects no app but still runs the site build, with its per-app checks over every app. A package's `test/` reaches only the apps that read from it. A JavaScript module or JSON file under `packages/components/src` reaches only the apps that load it (`scripts/lib/shared-module-users.mjs`: import specifiers and paths in each user's text, followed through the package's imports; a directory reference loads that directory, and a computed or unresolved one the whole package); declaration files, styles and every other file of the package still reach all its users. A root script that reads a list of component modules from the source directory declares the list in `LISTED_READS` there. A `packages/*/package.json` change that only adds `exports` entries selects nothing. Markdown outside `apps/` that no runtime reads, app-scoped agent guides (`apps/<id>/(AGENTS|AGENT|CLAUDE).md`, unless another app's code reads them via `appReaders`), `.github/aw/` compiler lock metadata, root `package.json` scripts neither `ci.yml` nor any workspace manifest calls, unreached lint tooling and other workflows select nothing; every root script a `ci.yml` job runs, directly or through another script, is an input (`jobScripts` in the workspace graph, read from `ci.yml`: one only the site jobs run selects the site build, any other every app), and a root script a workspace invokes via `pnpm -w` or `pnpm --workspace-root` (`workspaceRootScripts`) selects whatever reaches that workspace; an offline asset lock change selects the apps whose assets changed. A `pnpm-lock.yaml` change selects the apps that reach an importer whose entries or resolved dependency closure changed, before or after (`scripts/lib/lockfile-impact.mjs`); a change to the root importer, to a section other than importers, packages and snapshots, or one the planner cannot resolve selects every app. A `registry/apps.yml` change selects the apps whose entries changed and the site build, and also the apps that render the handoff catalog every app page carries (those naming `HANDOFF_CATALOG_READERS`, today DICOM View) when an entry changes what it lists (`handoffCatalogEntry` on the hosts `appCatalogIds` names); a change to which apps are registered also selects the apps that reach `AUTOMATION_CATALOG_READERS`; a changed entry field outside `CLASSIFIED_ENTRY_FIELDS` selects every app. `SITE_KEY_READERS` lists every key of the `site` section; a changed key selects the apps that reach a file it lists for that key, once the head registry validates (every app build validates all of it). A key only the site build reads (the hub, the analytics period, categories) selects only the site build, and a key the composite build writes into every app page it assembles (a catalogue's id, host, title or brand, the analytics id; every key outside `SITE_DATA_KEYS`) makes the per-app site checks cover every app; the desktop scripts that hold a whole catalogue entry read every catalogue key. A key the table does not list, at any depth and whatever its value, anywhere in the base or head section (key paths are compared as raw segments, so a key containing a dot or bracket is one it does not list), an invalid head registry, or a change outside `site` and the app entries selects every app. `test/app-plan.test.mjs` reads the text of every file an app build or app test runs that loads the registry or reads `site` for the keys it reads, counts any use of the registry object it does not recognise, a computed member or computed destructuring included, as reading every key, and fails when the table does not list the file for one. A `registry/app-information.yml` change whose head file passes `validateAppInformation` selects the apps whose entries changed and the site build; an invalid file or a change to `shared` or any other section selects every app. A `registry/standalone.json` change whose head catalog passes `validateStandalone` selects the apps whose entries changed and the site build (a suite-only change selects only the site build); an invalid catalog or a change to any other field selects every app. A root `.gitattributes` change counts as a change to every file whose attributes git resolves differently at the merge base and at head (`git check-attr --source`); if that comparison fails, it selects every app. `runtime-assets/manifest.json` selects the apps that reach `scripts/fetch-app-runtime.mjs` and the site build; an app's `automation.json` also selects the apps that reach `scripts/lib/neuroflow-bundle.mjs`, which generates NeuroFlow tools from every contract; the landing page, `site/analytics.json`, `site/404.html` and `site/dicompare-routes.js` select only the site build (and, like every `site/` file, the easter egg). `test/app-plan.test.mjs` fails when another file reads either. Without the base text of either file the planner selects every app. The plan job lists why it selected each app, or why it fell back, in its summary and `selection_reasons` output. Root configuration (`package.json` dependencies except root-only Knip, Stryker and ESLint devDependencies, and `pnpm-workspace.yaml` outside validated exact-version `minimumReleaseAgeExclude` edits whose removed entries are no longer resolved in head `pnpm-lock.yaml`) still selects every app. `scripts/lib/e2e-test-data.mjs` narrows to the apps whose pure provisioner entries changed (running their `@heavy` browser tests) when shared helpers, `provisionTestData` dispatch, and syntax validation are intact; plain-string `unpublished` reason edits select no apps. A `ci.yml` change is compared job by job (`CI_JOB_SCOPES`), and narrows only when the base and head have the same jobs and no job of another scope needs a changed job, or is needed by it, at the base or the head: one confined to `composite-site` or a job that only consumes its build (the five site checks, `processing-workflows`, `agent-interactions`, `example-cache-retention`) selects only the site build, with its per-app checks over every app; one confined to `homepage-easter-egg` runs it and no app; one confined to `workspace-contracts` (which runs on every run) or the `full-plan` marker jobs selects nothing more; an added or removed job, a `needs` link across scopes, a change to the plan, a per-app job, any other job or a key outside `jobs` (`on`, `env`, `concurrency`, `permissions`, `defaults`), or one without both texts, selects every app. `test/ci-required-jobs.test.mjs` runs in `app-plan` (`pnpm check:integration`) and in `workspace-contracts` (`pnpm test:contracts`) and fails when a job the CI policy needs is missing, carries `continue-on-error`, runs under another condition or waits for other jobs than it pins, needs a job that can be skipped on a run where it is due (it simulates every trigger with every value of the outputs job conditions read; a condition with a status function that admits a skipped dependency may), or has a run step that can be skipped other than as it lists, or when either guard step is missing, conditional or soft. A change that removes both guards is caught only by review and by the full plan it triggers. The nightly run tests every app whatever a change selected. `package-tests` runs every package test (`pnpm test:packages` + `exes/nii2tvx`) on ready pull requests, pushes and nightlies; package suites are not narrowed, because what a suite reads cannot be found from its text, and drafts skip `package-tests` only when every changed path lies in `docs/`, `.changeset/`, `site/easter-eggs/`, root Markdown, or scoped `(AGENTS|AGENT|CLAUDE).md` guides under `apps/`, `packages/`, or `exes/`. `homepage-easter-egg` runs on every push, nightly and dispatch but `scope=gpu`, even when the plan fails. A pull request skips it only when the plan succeeded and wrote `skip` to its `easter_egg` output; any other value, an empty one included, runs it. The plan writes `skip` only when every changed path lies in a tree the job cannot read (`easterEggCannotRead` in `scripts/lib/app-plan.mjs`): `apps/`, `exes/`, `models/`, `docs/` and every package but `packages/analytics`, a workspace manifest there (`WORKSPACE_MANIFESTS`: `package.json`, `package.json5`, `package.yaml`, each of which pnpm reads as its own project) excepted; any other path, `test-utils/`, `.github/`, `.changeset/` and every root file included, runs it. `EASTER_EGG_INPUTS` lists the files the job reads, and `test/app-plan.test.mjs` holds it to the job's commands, the code they run and the files its environment names, and holds every one outside the skip trees. A draft plans it as a ready pull request does. Knip and Stryker run in the independent `quality` workflow and ESLint (`eslint`, `@eslint/js`, `globals`) only in workspace-contracts and that workflow's correctness job; their root-only closure is omitted only after validating all resolutions, and other importers keep their full closures. When a pull request selects the whole catalog, the macOS GPU suite runs after merge and nightly instead; dispatch `ci` on the branch with `-f scope=gpu` to run only that suite first. A dispatched `ci` run tests what its branch changed since it left main (`scope=affected`, the default; on main, as a push does), only the GPU suite of those apps (`gpu`), only the composite site, agentic checks and easter egg (`site`), or every app (`all`); like a pull request, `affected` builds the composite site only when its plan needs it, so pass `scope=site` with `agentic_mode`. Release bookkeeping selects nothing: a `CHANGELOG.md`, a workspace `package.json` whose only change is its `version`, and a version-only change at an `EMBEDDED_VERSION_SITES` site (`scripts/lib/release-bookkeeping.mjs`); workspace-contracts checks that they agree on every run, and the nightly run builds every app at the new versions. `release.yml` plans with `--release`, where version bumps still select the apps they reach. Portable Node package workflows build on linux-x64 for pull requests and on every target after merge, on manual runs and on releases. `node-cli.yml` builds one package on every target when the shared packager changes. A native or CLI workflow that filters on a whole package also lists every file that package's command line imports from other workspace packages (`scripts/lib/module-closure.mjs` follows its bin and Node entry points); `test/independent-workflows.test.mjs` fails on a gap. A package path written in a root script is an edge even in prose (a reason string, a message), so name a package there only where the script reads it; `test/app-plan.test.mjs` fails when a package other than `components`, `runtime-support` and `analytics` is reached by most apps. `test/app-plan.test.mjs` and `test/independent-workflows.test.mjs` hold these rules. Before narrowing selection further, replay the planner over merged PRs with `scripts/app-plan-shadow.mjs` (it reports app misses against an independent oracle, and lists the rows narrowed by site keys or `ci.yml` jobs, which it has no expectation for) and measure with `scripts/ci-minutes-report.mjs`; [the October 2026 report](../../docs/quality/ci-selection-shadow-2026-10.md) and [the November 2026 replay](../../docs/quality/ci-development-tiers.md#site-keys-ciyml-jobs-and-the-fixed-jobs) hold the last results. The nightly run has its own concurrency group so a push to main cannot cancel it. Main CI lets the running push finish and coalesces pending pushes. A push diffs from the head of the nearest finished `ci` run on main (push or nightly, since a dispatch can test part of the plan; `resolveCiBase` in `scripts/lib/tested-base.mjs`), not from its own `before`: it tests every merge since then, including merges whose runs were cancelled. When that run failed, the push also selects the apps whose `app-tests` or browser jobs did not pass there, without their `@slow` tests; when a failed job belongs to no app (the plan itself, or a site job, which checked only its own run's apps), has not finished, or names an app the registry does not know, it diffs from the last green run instead. Without such a run among the newest 100, or when its head is not an ancestor, the push selects every app.

A workflow that builds on a shared tree (`packages/components/**`, `pnpm-lock.yaml`, `registry/**`, `scripts/**`) lists those filters in its gate job's `shared_paths`, never in its pull request `paths`; it starts with a `gate` job calling `.github/workflows/pr-gate.yml`, and its entry jobs wait for `needs.gate.outputs.run`. A pull request that changes a shared path starts one workflow, `native.yml`, not each workflow that builds on it: its gate (`pr-gate.yml` with `workflow: native`) decides for every workflow with `shared_paths`, and it calls the ones that run through `workflow_call`, on the pull request's own event and commit. A workflow whose own paths changed starts itself, and its gate decides with both kinds of filter; `native.yml` skips it, with the explicit verdict "starts itself", only when that own start is certain (`certainOwnStart`: below GitHub's 3,000-file limit, no rename or copy, no exclusion filter, a plain path under a filter form it models), so a workflow can run twice but never not at all. Running is the default: each call's generated `if:` (`callCondition` in `scripts/lib/native-workflow.mjs`) skips it only when the gate succeeded and names the workflow in its `skips` output, the JSON array of workflows it decided, each one explicitly, to skip. Absence means run, so a gate that fails, times out or is skipped, and a missing, empty, truncated or unknown list, run every workflow. A draft names every workflow in the gate's `calls` list (generated into `native.yml`), and the decide step passes on only names from `calls`, or `sweeps` on the schedule. A budget denial the gate confirmed is the one exception: it writes `withheld=true` first, every call skips and the `full-plan-withheld` job fails the run. Inside, the decision fails open too (`scripts/lib/native-decision.mjs`): whatever it cannot read or decide within five minutes, the budget reads included, runs. Read changed paths with `readChangedPaths` (`git diff -z`), never trimmed, and keep an unreadable diff apart from an empty one; a path it does not model counts as reaching every shared filter. `node scripts/native-workflow.mjs` writes `native.yml` from the workflow files; run it after adding or changing `shared_paths` (`test/workflow-gate.test.mjs` fails when it is stale). One run holds every workflow it calls, so a called workflow names its artifacts and its concurrency group after itself, and GitHub allows one workflow file at most 50 unique reusable workflows, nested ones included (the same test checks the count). For a ready pull request whose only matches are shared, `scripts/lib/workflow-gate.mjs` runs the workflow when a script it runs loads a changed file (any script of a package it owns, or a root script a step names), when the lockfile resolves a package it owns differently, or when the app planner selects an app it filters on; anything it cannot decide runs. Drafts answer false and dispatches true. A push runs the workflow unless every path under its `push` filter that changed since it last finished green on main (push or sweep) is release bookkeeping and no path under its `shared_paths` changed; the sweep asks the same two questions, since either run can skip and still finish green. A ready pull request over its full-plan budget fails the gate, even for the workflow's own paths, where its `ci` run withholds the full plan too. A workflow whose `push` filter covers a whole app, package or `exes/` directory also calls the gate, so release bookkeeping starts it neither for a pull request nor for a push; without `shared_paths`, its schedule stays a plain nightly run. A workflow with `shared_paths` lists only its own paths in its `push` filter and has no `schedule` of its own: shared paths reach it on main through `native.yml`'s nightly run, the sweep of every workflow it calls that a push also starts, which runs the workflow when a path under its `shared_paths` changed on main since the workflow last finished green there, in its own push run or its part of a scheduled `native.yml` run (a failed or dropped sweep keeps that commit, so the next one still sees the change). The sweep leaves release bookkeeping aside: a `CHANGELOG.md`, a workspace `package.json` whose only change is its `version`, and a valid `registry/standalone.json` in which no entry of the workflow's apps changed. A gate job grants `contents: read`, `actions: read` and `pull-requests: read`. Never add a shared path to such a `push` filter; to test a shared change on every target before merging, dispatch the workflow on the branch. Keep the gate job unconditional: a skipped gate skips every job after the entry jobs. `test/workflow-gate.test.mjs` holds these rules; [CI development tiers](../../docs/quality/ci-development-tiers.md#pull-request-gate-for-shared-path-filters) explains them. `neuroflow.yml` and `sdc-registration-gate.yml` take hours, so their pull request `paths` list only what they own; their gate only sets release bookkeeping aside. A merge starts `neuroflow.yml` on those same paths, and its nightly run covers the trees its apps build on; the SDC gate also starts on main for the files it imports from other packages (dispatch either on the branch to test a shared change first).

`ci-usage.yml` reports each day's workflow runs and fails, which opens an issue, when a budget in `scripts/lib/ci-usage.mjs` is exceeded: more than 2 whole-catalogue `ci` runs for one pull request or more than 10 in total ([budgets](../../docs/quality/ci-development-tiers.md#daily-usage-budget)). `node scripts/ci-usage-report.mjs --until <ISO time>` reports any day. Its report-only measures (minutes per merged PR, fixed-job share, ready to green, merge to live) classify jobs through `WORKFLOWS` in `scripts/lib/ci-measures.mjs`; a new or renamed workflow or `ci` job needs an entry there, which `test/ci-measures.test.mjs` enforces ([measures](../../docs/quality/ci-development-tiers.md#daily-measures)). The app planner enforces a per-pull-request budget too: a ready PR whose earlier `ci` runs in the last 24 hours already include 2 full-plan runs (runs that started the `full-plan` marker job because the full plan tests more apps than the draft plan, or whole-catalogue runs; `ready_for_review` and cancelled runs included) gets the draft plan and a failing `full-plan-withheld` job, and its gated native workflows fail their gate. Convert the PR to draft while iterating; to test every app at its head, add the `full-ci` label and use "Re-run all jobs" on `ci`, on `native` and on each native workflow whose gate failed ([enforcement](../../docs/quality/ci-development-tiers.md#enforcement-in-ci)).

Pull requests and pushes to main skip Playwright tests tagged `@slow`; nightly and manual runs include them. Release browser tests also select the full suite, subject to their data requirements. Tag a test `@slow` (`{ tag: '@slow' }`) only when an untagged or `@heavy` test completes a run with the same model, method, option and kind of geometry. A browser reference case that is the only completed run of a path stays untagged unless it is `@heavy`. Tag a browser test `@heavy` when it takes more than 5 minutes in the CPU `browser-e2e` job of a whole-catalogue run (the per-test durations below); the macOS GPU job runs it whatever the change. On pull requests and pushes to main, an app's `@heavy` tests in the CPU job run only when the change edits the app itself (its `apps/`, `packages/` or `exes/` directory or `models/<id>.manifest.json`, release bookkeeping and scoped `(AGENTS|AGENT|CLAUDE).md` guides aside) or a failed run on main left it untested; an app reached only through shared code leaves them to the nightly run (`heavy_tests` in the browser matrices, `NEURODESK_E2E_SKIP_HEAVY`). Dispatched, nightly and release runs include them. An app with tagged tests spreads `e2eTier` from `test-utils/e2e-tier.mjs` into its Playwright config (the shared config builders already do); `test/e2e-tier.test.mjs` checks it. The browser jobs in `.github/workflows/ci.yml` log per-test durations for tagging decisions.

`composite-site` builds the site once and uploads `dist/`; `site-runtime`, `site-audit`, `site-e2e`, `site-mobile` and `site-catalog` check that build in parallel, and `agent-interactions`, `processing-workflows` and `example-cache-retention` wait for all of them. The build artifact is kept 3 days; after that, "Re-run all jobs" rebuilds it. Checks that read `dist-sites/` or the per-app builds (`audit:artifacts`, `runtime-assets.test.mjs`, `catalog-sites.test.mjs`) stay in `composite-site`. On pull requests and pushes the per-app site checks (runtime startup, the interface audit, the composite smoke, the e2e catalog, interface workflows and mobile layouts) cover the apps the plan selected and one canary per shell (`CANARY_APPS` in `scripts/lib/smoke-apps.mjs`), through `SMOKE_APPS`. They cover every app on the nightly run, on a dispatch with `scope=all` or `scope=site`, when the plan selects every app, and when the plan's `site_code` output is true: the change reaches code the site jobs run (a check, the composite build or what they import, a site job of `ci.yml`, a `site` key written into every app page). Landing page files, registry, app information and standalone entries, the offline lock and the `site` keys in `SITE_DATA_KEYS` are data and leave it false. Catalogue-level checks run whenever the site is built. An unknown `SMOKE_APPS` id or canary, or a narrowed check that checks no app, fails. A narrowed check is sound only where its result for an app depends on that app alone: a check that compares an app with others or reads another app's files declares `needs` (the apps to add when an app is listed, derived from the facts it reads, or null for every app), and `smokeApps` adds them before it runs ([composite site checks](../../docs/quality/ci-development-tiers.md#composite-site-checks)).

The nightly `agent-interactions` job runs each viewport's catalog in three `--shard` slices on one worker each: agent-action latency varied nearly threefold between nightlies in November 2026, and the unsharded catalog no longer fit 120 minutes at the slow end. An app can set `ci.e2e_shards` to 2-4 in `registry/apps.yml`. The CPU browser job splits its selected tests by spec file unless the Playwright config is `fullyParallel`; unit/build and hardware GPU jobs stay unsharded. CI builds each app before its browser tests and sets `NEURODESK_E2E_PREBUILT=1`, so the example smoke driver uses that production bundle. Its standalone invocation retains the normal build. Rust jobs restore Cargo build directories using lockfile-based cache keys, including the shared Greedy workspace.
